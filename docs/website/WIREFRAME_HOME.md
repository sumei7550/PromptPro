# PromptPro 首页 Wireframe

更新时间：2026-08-23

本文档冻结 PromptPro 首页的结构和响应式规则，覆盖 Desktop 1440px、1280px 以及 Mobile 390px、360px 四个基准视口。本阶段不定义颜色、字体、视觉稿、营销文案或 React 实现；组件名称仅用于说明后续实现边界。

## 1. Wireframe 原则

### 1.1 设计基准

首页必须同时设计以下四个视口：

| 类型 | 基准宽度 | 用途 |
|---|---:|---|
| Desktop Wide | 1440px | 宽屏主布局、完整导航和内容密度基准 |
| Desktop Standard | 1280px | 常见桌面布局和折行检查 |
| Mobile Standard | 390px | 常见手机首屏和触摸交互基准 |
| Mobile Narrow | 360px | 窄屏折行、按钮和菜单边界检查 |

1440px 和 1280px 共用同一信息架构，但允许容器宽度、双栏比例和卡片间距按可用空间收缩。390px 和 360px 共用同一内容顺序，但不是 Desktop 的缩小版：导航、Hero 顺序、卡片排列、CTA 宽度和 Footer 行为均单独定义。

### 1.2 页面总结构

首页固定采用以下纵向顺序：

```text
Header
  ↓
Hero
  ↓
Product Preview
  ↓
Feature Section
  ↓
Privacy Section
  ↓
Platform Section
  ↓
Template Section
  ↓
Final CTA
  ↓
Footer
```

该顺序对应当前信息架构中的首页职责：先说明产品，再展示能力和真实界面，然后处理信任、平台边界、模板入口和安装转化。

### 1.3 内容边界

- 首页只展示已确认的产品能力和平台状态；
- 不把平台配置写成稳定支持；
- 不把未确认的模板数量、用户数量、评分或成功率放入布局要求；
- 不使用云端模型、完全离线或所有平台兼容等未经事实支持的表达；
- Product Preview 必须最终使用真实扩展界面截图；当前只冻结截图容器和裁剪规则，不冻结具体素材；
- 文案内容由后续 Copy Deck 阶段决定，本文件只冻结信息位置和内容类型。

## 3. Header

### 3.1 目的

提供全站导航、当前语言上下文、安装入口，并让用户在任何首页滚动位置都能理解返回路径。

### 3.2 用户看到的信息

Desktop：

- Logo；
- Features；
- Platforms；
- Templates；
- Privacy；
- Language Switcher；
- Chrome Web Store CTA。

Mobile：

- Logo；
- Menu Button；
- 展开的 Mobile Navigation；
- Language Switcher；
- Chrome Web Store CTA。

### 3.3 Desktop 布局

1440px：

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Logo        主导航居中或靠左                     Language   CTA      │
└──────────────────────────────────────────────────────────────────────┘
```

1280px：

- 保持同一单行结构；
- Logo、导航、语言切换和 CTA 不得互相挤压；
- 如果可用宽度不足，优先压缩导航间距，不能缩小 CTA 到不可用尺寸；
- 不在 1280px 提前切换成 Mobile 菜单，除非实现阶段通过实际内容证明单行布局无法成立。

### 3.4 Mobile 布局

390px 和 360px：

```text
┌──────────────────────────────┐
│ Logo                    Menu  │
└──────────────────────────────┘
```

Menu Button 打开后：

```text
┌──────────────────────────────┐
│ Logo                  Close  │
├──────────────────────────────┤
│ Features                     │
│ Platforms                    │
│ Templates                    │
│ Privacy                      │
│ Language Switcher            │
│ Chrome Web Store CTA         │
└──────────────────────────────┘
```

菜单结构采用垂直列表，不把 Desktop 导航压缩成难以点击的横向链接。CTA 在展开菜单中使用独立的可点击区域，语言切换保留当前页面对应语言关系。

### 3.5 响应式变化规则

- Desktop 使用完整导航；Mobile 使用 Menu Button；
- Mobile 菜单打开时必须有关闭入口；
- 菜单项按页面职责顺序排列，不按 Desktop 的横向位置机械换行；
- 语言切换不得跳转到空白或 TODO 页面；
- CTA 必须在 390px 和 360px 中完整显示；
- Header 不承担 Hero 的产品说明，避免首屏信息过载。

### 3.6 后续对应组件

- `SiteHeader`；
- `DesktopNavigation`；
- `MobileNavigation`；
- `LanguageSwitcher`；
- `InstallCta`。

## 4. Hero 首屏

### 4.1 目的

在用户首次进入页面时说明产品类别、主要使用场景和下一步行动，并让用户快速看到真实产品界面。

### 4.2 用户看到的信息

- 产品定位标题区域；
- 简短产品说明区域；
- 主安装 CTA；
- 次 CTA；
- 产品截图或产品预览；
- 产品是 Chrome 扩展这一入口信息。

本阶段不写具体营销文案，只冻结这些信息的相对位置。

### 4.3 Desktop 布局

1440px 和 1280px 均采用左右双栏：

```text
┌──────────────────────────────────────────────────────────────────────┐
│                                                                      │
│  左栏：标题、描述、CTA                 右栏：产品截图                 │
│  ┌─────────────────────────┐          ┌─────────────────────────┐   │
│  │ 标题区域                │          │                         │   │
│  │ 描述区域                │          │ 真实插件界面截图         │   │
│  │ 主 CTA   次 CTA         │          │ 完整 UI，不裁切核心区域   │   │
│  └─────────────────────────┘          └─────────────────────────┘   │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

布局规则：

- 左栏承担标题、描述和 CTA；
- 右栏承担产品截图，不在 Hero 中再放第二组复杂信息；
- 标题区域和描述区域共享左栏宽度，但描述可以比标题窄；
- CTA 位于描述之后，主 CTA 在前，次 CTA 在后；
- 1440px 允许较宽的右侧截图区域；
- 1280px 缩小两栏间距和截图显示宽度，但保留左右结构；
- 不把截图放到页面底部才首次出现，首屏需要给出真实产品预览。

### 4.4 Mobile 布局

390px 和 360px 采用单列，并优先让用户理解产品再看截图：

```text
标题区域
    ↓
描述区域
    ↓
主 CTA（全宽）
    ↓
次 CTA
    ↓
产品截图
```

规则：

- 标题和描述默认居中对齐，具体文字长度由 Copy Deck 决定；
- 主 CTA 在 390px 和 360px 均使用接近容器宽度的全宽按钮；
- 次 CTA 保持可见，但不与主 CTA 争夺同等视觉优先级；
- 图片位于 CTA 之后，避免截图挤压首屏产品定位；
- 截图完整显示或按比例缩放，不使用 `cover` 隐藏核心 UI；
- 若完整截图在 360px 高度过长，允许通过页面纵向滚动展示，但不允许截断核心操作区域。

### 4.5 响应式变化规则

- Desktop：左右双栏；Mobile：单列；
- Desktop 标题区域左对齐，Mobile 默认居中；
- Desktop CTA 可水平排列，Mobile 主 CTA 独占一行；
- Desktop 截图位于右栏，Mobile 截图移动到 CTA 后；
- 1280px 不改变信息层级，只收缩可用空间；
- 360px 不删除产品定位、主 CTA 或核心截图，只允许减少装饰性间距。

### 4.6 后续对应组件

- `HeroSection`；
- `HeroCopy`；
- `InstallCta`；
- `SecondaryCta`；
- `ProductScreenshot`。

## 5. Product Preview

### 5.1 目的

用真实扩展界面解释 PromptPro 的实际使用形态，建立产品可信度，并为后续功能说明提供视觉锚点。

### 5.2 用户看到的信息

- 真实插件界面截图；
- 截图对应的产品上下文；
- 必要时提供简短的使用步骤区域，但不在本阶段写具体文案。

### 5.3 素材规则

- 最终必须使用真实扩展界面截图或已确认的真实产品素材；
- 当前最终截图、版本和裁剪方式尚未冻结，本 Wireframe 只保留截图容器；
- 禁止使用 AI 生成的 UI 图作为真实功能证明；
- 禁止使用 `cover` 裁切核心 UI；
- 截图中输入框、优化结果、模板入口等核心区域不能被隐藏；
- 截图必须保留完整可理解的界面上下文，并在素材清单阶段记录来源和版本。

### 5.4 Desktop 布局

1440px：

- 使用宽幅预览区域；
- 截图按原始比例缩放；
- 截图周围保留足够空间，避免边缘 UI 被视觉容器遮挡；
- 如需并列多个截图，最多并列展示两个，并保持每张截图完整可读。

1280px：

- 优先保留一张完整主截图；
- 第二张截图可以转为下方纵向排列，不强行压缩为不可读缩略图；
- 不通过裁切解决容器宽度不足。

### 5.5 Mobile 布局

390px 和 360px：

- 默认单张截图纵向展示；
- 截图宽度不超过内容容器；
- 按原始比例缩放；
- 如果有多张截图，采用纵向堆叠，而不是横向压缩成无法阅读的缩略图；
- 不使用横向滚动隐藏核心 UI；
- 允许页面继续向下滚动展示完整截图。

### 5.6 响应式变化规则

- 桌面端通过容器宽度变化缩放，不改变截图内容；
- 移动端由多栏变单列；
- 图片可以自然高度增长，不能固定高度后裁切；
- 截图比例由素材决定，容器不得强制改变比例；
- 未冻结真实素材前，不得把占位图作为发布资产。

### 5.7 后续对应组件

- `ProductPreviewSection`；
- `ProductScreenshot`；
- `ScreenshotCaption`；
- `HowItWorksPreview`。

## 6. Feature Section

### 6.1 目的

集中解释 PromptPro 已确认的核心能力，并将用户从 Hero 的产品认知引导到具体使用价值。

### 6.2 用户看到的信息

六项能力：

- Prompt 优化；
- 模板库；
- 自定义模板；
- 优化历史；
- 双语体验；
- 本地数据管理。

每项能力只展示已确认的功能范围，不在 Wireframe 阶段添加新的产品承诺。

### 6.3 Desktop 布局

1440px 和 1280px 使用卡片网格：

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Section 标题 / 说明                                                  │
├──────────────────────┬──────────────────────┬────────────────────────┤
│ Prompt 优化           │ 模板库               │ 自定义模板             │
├──────────────────────┼──────────────────────┼────────────────────────┤
│ 优化历史              │ 双语体验             │ 本地数据管理           │
└──────────────────────┴──────────────────────┴────────────────────────┘
```

- Desktop 固定为 3 列 × 2 行；
- 1440px 可以使用更宽的卡片内容区；
- 1280px 保持 3 列，但收缩卡片间距和内边距；
- 每张卡片拥有相同的信息层级：能力名称、简短说明、可选的真实界面关联；
- 不在首页为每项能力创建过深的子导航。

### 6.4 Mobile 布局

390px 和 360px 使用单列堆叠，顺序为：

```text
Prompt 优化
↓
模板库
↓
自定义模板
↓
优化历史
↓
双语体验
↓
本地数据管理
```

- 不使用横向滚动承载核心功能卡片；
- 每张卡片完整显示名称和说明；
- 卡片高度由内容自然决定；
- 不在 Mobile 隐藏后两项能力；
- 如果未来增加真实截图，截图位于对应卡片内部或整个 Feature Section 之后，不改变能力顺序。

### 6.5 响应式变化规则

- Desktop：3 列 × 2 行；
- Mobile：单列 6 张卡片；
- 1280px 不降为 2 列，除非最终文案长度证明 3 列不可读；
- 360px 优先保持说明可读，不通过缩小文字解决空间问题；
- 六项能力的顺序在语言版本之间保持语义一致。

### 6.6 后续对应组件

- `FeatureSection`；
- `FeatureGrid`；
- `FeatureCard`。

## 7. Privacy Section

### 7.1 目的

在用户完成能力了解后，解释数据处理和使用边界，建立安装前信任。

### 7.2 用户看到的信息

三项核心信息：

- 无需账号；
- 本地存储；
- 提示词不上传到新的远程服务。

这些是信息类别，不是本阶段的正式营销文案。最终表述必须与产品事实、扩展隐私页和 Manifest 保持一致。

### 7.3 Desktop 布局

使用“说明区 + 三项信任信息”的横向结构：

```text
┌──────────────────────────────┬───────────────────────────────────────┐
│ Section 标题 / 说明           │ 无需账号                              │
│                              ├───────────────────────────────────────┤
│ 查看 Privacy 详情的次 CTA      │ 本地存储                              │
│                              ├───────────────────────────────────────┤
│                              │ 提示词不上传到新的远程服务              │
└──────────────────────────────┴───────────────────────────────────────┘
```

- 1440px：左侧说明区较宽，右侧三项纵向排列；
- 1280px：保持左右结构，缩小两栏间距；
- 不使用复杂数据流图，避免在首页形成难以维护的隐私解释。

### 7.4 Mobile 布局

单列顺序：

```text
Section 标题 / 说明
↓
无需账号
↓
本地存储
↓
提示词不上传到新的远程服务
↓
查看 Privacy 详情
```

- 三项信息完整堆叠；
- 长文本允许自然换行；
- CTA 使用独立行，不和隐私说明挤在同一行；
- 不隐藏存储和远程请求边界。

### 7.5 响应式变化规则

- Desktop：说明区与信息区并列；
- Mobile：说明和三项信息纵向堆叠；
- 360px 不通过截断或省略号隐藏隐私边界；
- 隐私信息优先保持完整可读，装饰元素可以移除；
- 语言切换后保留相同信息层级，不因英文或中文长度改变事实范围。

### 7.6 后续对应组件

- `PrivacySection`；
- `PrivacyFeatureList`；
- `PrivacyFeatureItem`；
- `PrivacyLink`。

## 8. Platform Section

### 8.1 目的

展示平台适配信息，同时明确区分历史验证和当前仅配置未验证的平台，避免把平台配置误认为稳定支持承诺。

### 8.2 用户看到的信息

两个明确分组：

#### 历史验证

- ChatGPT；
- Claude；
- Gemini；
- DeepSeek。

状态语义：历史验证通过，本轮未复测。

#### 已配置未验证

- 其他已配置平台；
- 具体平台列表和展示数量以当前验证文档冻结结果为准。

状态语义：代码配置，未验证。

页面还需要显示统一的平台边界说明：平台可用性以当前版本实际验证情况为准。

### 8.3 Desktop 布局

使用分组标题 + 状态 Badge + 平台卡片：

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Section 标题 / 平台边界说明                                          │
├──────────────────────────────────────────────────────────────────────┤
│ 历史验证：历史验证通过，本轮未复测                                   │
│ ┌──────────────┬──────────────┬──────────────┬──────────────┐        │
│ │ ChatGPT      │ Claude       │ Gemini       │ DeepSeek     │        │
│ │ 状态 Badge   │ 状态 Badge   │ 状态 Badge   │ 状态 Badge   │        │
│ └──────────────┴──────────────┴──────────────┴──────────────┘        │
├──────────────────────────────────────────────────────────────────────┤
│ 已配置未验证：代码配置，未验证                                       │
│ ┌──────────────┬──────────────┬──────────────┬──────────────┐        │
│ │ 其他平台     │ 其他平台     │ 其他平台     │ 其他平台     │        │
│ │ 状态 Badge   │ 状态 Badge   │ 状态 Badge   │ 状态 Badge   │        │
│ └──────────────┴──────────────┴──────────────┴──────────────┘        │
└──────────────────────────────────────────────────────────────────────┘
```

- 1440px：历史验证组可以使用 4 列卡片；未验证组按实际平台数量使用 4 列或多行；
- 1280px：仍优先保持历史验证组 4 列，卡片内容只保留平台名称和状态 Badge；
- 两个分组之间必须有清晰的分组标题和状态解释；
- 不用一个混合列表把两种状态混在一起；
- 不使用“稳定支持”“完全兼容”等状态标签。

### 8.4 Mobile 布局

每个状态组独立展示：

```text
历史验证标题 + Badge 说明
    ↓
[ChatGPT] [Claude] [Gemini] [DeepSeek]  → 横向滚动

已配置未验证标题 + Badge 说明
    ↓
[平台] [平台] [平台] ...                 → 横向滚动
```

- 平台卡片采用横向滚动，避免大量平台把首页拉得过长；
- 两个状态组不能共用同一个横向滚动列表；
- 每张卡片必须完整显示平台名称和状态 Badge；
- 横向滚动区域需要有可见的继续滚动提示或足够的卡片露出，但不依赖颜色表达状态；
- 若最终平台数量很少，可以改为单列堆叠，但必须保持状态分组不变；
- 未验证平台不在 Mobile 中隐藏状态说明。

### 8.5 响应式变化规则

- Desktop：分组卡片网格；
- Mobile：按状态分组的横向卡片列表，必要时退化为单列；
- 1440px 与 1280px 不合并两个状态组；
- 平台名称过长时允许换行，不能用裁切隐藏名称；
- 状态 Badge 必须以文字表达，不依赖颜色；
- 平台真实验证状态变化时，只更新对应数据和状态，不改变整体结构。

### 8.6 后续对应组件

- `PlatformSection`；
- `PlatformGroup`；
- `PlatformCard`；
- `PlatformStatusBadge`；
- `PlatformDisclaimer`。

## 9. Template Section

### 9.1 目的

展示模板库的真实分类和入口价值，让用户理解 PromptPro 不只是提示词优化器，也提供可搜索、可复用的双语模板能力。

### 9.2 用户看到的信息

8 个已确认的内置模板分类：

- 写作；
- 职场；
- 编程；
- 翻译；
- 营销；
- 学术；
- 分析；
- 创意。

分类卡片是入口，不在本首页 Wireframe 中创建 8 个独立 SEO 页面。分类内容、真实模板示例和数量必须在内容审查阶段按实际数据冻结。

### 9.3 Desktop 布局

使用 4 列 × 2 行卡片网格：

```text
┌──────────────────────────────────────────────────────────────────────┐
│ Section 标题 / 模板入口说明                                          │
├──────────────────┬──────────────────┬──────────────────┬──────────────┤
│ 写作             │ 职场             │ 编程             │ 翻译         │
├──────────────────┼──────────────────┼──────────────────┼──────────────┤
│ 营销             │ 学术             │ 分析             │ 创意         │
└──────────────────┴──────────────────┴──────────────────┴──────────────┘
```

- 1440px：4 列 × 2 行；
- 1280px：保持 4 列，必要时收缩卡片宽度和间距；
- 每张卡片至少有分类名称和进入模板页的入口；
- 如加入真实模板示例，所有卡片保持相同信息层级；
- 不在本阶段冻结具体颜色、图标或卡片装饰。

### 9.4 Mobile 布局

390px 和 360px 默认使用横向滚动分类列表：

```text
[写作] [职场] [编程] [翻译] →
[营销] [学术] [分析] [创意] →
```

- 采用横向滚动，避免 8 个分类造成过长的首页；
- 每个卡片完整显示分类名称；
- 至少露出一个半卡片或其他明确的继续滚动线索；
- 不把 8 个分类压缩成不可读的两列小卡片；
- 如果后续真实内容需要用户快速比较所有分类，可以在实现阶段评估单列堆叠，但必须保留 8 类顺序和完整可读性。

### 9.5 响应式变化规则

- Desktop：4 列 × 2 行；
- Mobile：横向滚动分类卡片；
- 1280px 不默认降为 3 列，保持与 1440px 一致的信息密度；
- 360px 优先保证分类名称完整显示；
- 横向滚动只用于分类入口，不隐藏页面主 CTA；
- 真实模板示例若加入首页，应在分类卡片下方或模板页中展开，不把卡片变成不可读的多层嵌套。

### 9.6 后续对应组件

- `TemplateSection`；
- `TemplateCategoryGrid`；
- `TemplateCategoryCard`；
- `TemplateBrowseLink`。

## 10. Final CTA

### 10.1 目的

在用户完成产品、隐私、平台和模板理解后，提供明确的 Chrome Web Store 安装入口。

### 10.2 用户看到的信息

- Chrome Web Store 安装 CTA；
- 可选的简短行动说明区域；
- 返回功能或模板页的次链接可以作为辅助，但不能分散主 CTA。

本阶段不写 CTA 的最终营销文案。

### 10.3 Desktop 布局

```text
┌──────────────────────────────────────────────────────────────────────┐
│                     Final CTA 内容区                                 │
│                  Chrome Web Store CTA                                │
└──────────────────────────────────────────────────────────────────────┘
```

- 1440px 和 1280px 使用居中内容区；
- 主 CTA 作为独立按钮或链接区域，不与多个次 CTA 并列竞争；
- CTA 目标必须是最终复核并冻结的 Chrome Web Store URL；
- 不自动执行安装或插件操作。

### 10.4 Mobile 布局

- CTA 区域单列；
- 主按钮使用接近内容容器宽度的全宽按钮；
- 360px 中按钮文字不得截断或被左右内边距挤压；
- 如果存在次链接，放在主按钮下方独立一行；
- 不使用固定底部悬浮安装条，除非后续交互设计阶段单独批准并完成可访问性评估。

### 10.5 响应式变化规则

- Desktop：居中内容区和非全宽 CTA；
- Mobile：单列、全宽主按钮；
- CTA 文本长度变化时按钮仍必须保持完整可读；
- 主 CTA 在页面底部与 Header CTA 指向同一正式目标。

### 10.6 后续对应组件

- `FinalCtaSection`；
- `InstallCta`；
- `SecondaryCta`。
