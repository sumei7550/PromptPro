## 4. Environment Separation

Choose one strategy and record it before implementation.

### Preferred strategy: separate staging and production Projects

```text
PromptPro — Staging
PromptPro — Production
```

Advantages:

- test data cannot pollute production dashboards;
- production retention and access can be reviewed independently;
- live dashboards remain easier to interpret.

### Acceptable fallback: one Project with an explicit environment field

If the account plan makes separate Projects impractical, every event must include:

```json
{
  "environment": "staging"
}
```

or:

```json
{
  "environment": "production"
}
```

The values must be generated by deployment configuration, not inferred from an arbitrary hostname. Dashboard filters must exclude `staging` from production reports.

Current recommendation: use a separate staging Project if testing is expected to produce real events. If staging is never connected to Mixpanel, use a local no-op mode instead.

## 5. Identity and User Profile Settings

The current PromptPro website has no account or login system. The initial Project must remain anonymous.

- [ ] Do not call `identify`.
- [ ] Do not send email addresses.
- [ ] Do not send account IDs, login state, or subscription IDs.
- [ ] Do not send a user name or profile name.
- [ ] Do not enable cross-product identity merging.
- [ ] Do not connect website and extension identities by default.
- [ ] Confirm the SDK's anonymous `distinct_id` behavior.
- [ ] Confirm whether anonymous IDs persist between visits.
- [ ] Confirm whether anonymous IDs are stored in cookies, localStorage, sessionStorage, or another browser mechanism.
- [ ] Confirm whether an anonymous ID can be reset or deleted.
- [ ] Document the selected identity behavior in the private configuration record.

Required initial policy:

```text
Anonymous events only
No user profiles
No identity stitching
No email identity
No cross-product identity
```

If the selected SDK cannot meet the approved no-cookie/cookie-like-identifier boundary, stop before implementation and revisit the product/privacy decision.

## 6. Persistence, Cookies, and Consent

These items must be checked against the actual SDK version and current Project settings. Do not rely only on a generic Mixpanel tutorial.

- [ ] Confirm whether the SDK writes first-party cookies.
- [ ] Confirm whether the SDK writes localStorage or sessionStorage.
- [ ] Confirm whether the SDK reads existing cookies or storage.
- [ ] Confirm whether the SDK uses a generated identifier when persistence is disabled.
- [ ] Confirm whether the SDK can operate without cookie-like persistence.
- [ ] Confirm the effect of clearing browser storage.
- [ ] Confirm opt-out behavior and whether it prevents future events.
- [ ] Confirm opt-in behavior if a consent gate is required.
- [ ] Confirm whether Do Not Track is honored or must be implemented separately.
- [ ] Confirm whether consent state itself is recorded; if so, ensure it does not include identity or content.
- [ ] Obtain a product/privacy decision for the selected persistence and consent behavior.

Initial PromptPro boundary:

```text
Do not use cookies or cookie-like identifiers without explicit approval.
Do not enable tracking before the required consent/privacy decision.
Do not treat Mixpanel's default persistence as automatically approved.
```

## 8. Page-View Configuration

Select exactly one page-view source.

### Option A: Mixpanel automatic page views

- [ ] Initial `/` load is captured once.
- [ ] Initial `/zh-CN` load is captured once.
- [ ] Next.js client navigation is captured.
- [ ] Browser back/forward navigation is understood.
- [ ] The recorded URL is normalized safely.
- [ ] Query strings and fragments are not exposed in the approved reporting model.
- [ ] No custom `web_page_view` is added if this option passes.

### Option B: explicit `web_page_view`

- [ ] Automatic page views are disabled or excluded from dashboards.
- [ ] The explicit event is emitted once per viewed route.
- [ ] `page` contains only the normalized pathname.
- [ ] `locale` is `en` or `zh-CN`.
- [ ] `referrer_domain` is sent only if separately approved.
- [ ] Route transitions and back/forward behavior are tested.

Current recommendation: inspect automatic behavior first; do not implement both options.

## 9. Referrer, URL, and Country Settings

### URL

- [ ] Custom properties contain pathname only.
- [ ] Query strings are excluded.
- [ ] Fragments are excluded.
- [ ] Full Chrome Web Store URLs are not sent as event properties.
- [ ] Email addresses are not encoded into event properties.
- [ ] Internal or external link labels are not sent as arbitrary text.

### Referrer

- [ ] Confirm whether Mixpanel receives a full Referrer URL automatically.
- [ ] Disable full Referrer capture if it cannot be safely normalized.
- [ ] If enabled, reduce it to an approved hostname or source category.
- [ ] Confirm that search queries and sensitive URL parameters are not retained.
- [ ] Record the final `referrer_domain` decision.

Approved example:

```json
{
  "referrer_domain": "www.google.com"
}
```

Not approved:

```json
{
  "referrer": "https://www.google.com/search?q=user+query"
}
```

### Country

- [ ] Confirm whether country is derived from IP.
- [ ] Confirm whether the original IP is stored, masked, or discarded.
- [ ] Confirm country retention and deletion behavior.
- [ ] Confirm whether country reporting is needed for the MVP.
- [ ] Update Privacy wording if country is enabled.

Decision for PromptPro: enable IP-based Country derivation. Do not add raw IP as a custom event property. Review whether Mixpanel also exposes City/Region default properties; if they cannot be disabled, disclose that actual behavior before treating this gate as fully closed.

## 10. Event Schema Registration

The Project event dictionary should contain only the approved initial events:

| Event | Required properties |
|---|---|
| `web_page_view` | `page`, `locale`; optional approved `referrer_domain` |
| `web_cta_click` | `location`, `cta_name`, `page`, `locale` |
| `web_store_click` | `location`, `page`, `locale` |
| `web_language_switch` | `from`, `to`, `page`, `locale` |
| `web_external_click` | `target`, `page`, `locale` |
| `web_faq_expand` | `faq_id`, `page`, `locale` |

Allowed enum values:

```text
locale:    en | zh-CN
location:  header | hero | final_cta | footer | content
target:    github | kofi | email
```

Before implementation:

- [ ] Register or document the six event names.
- [ ] Register or document property types and enum values.
- [ ] Confirm `page` is pathname-only.
- [ ] Confirm `faq_id` is a stable slug, not the full FAQ question.
- [ ] Confirm Store links emit only `web_store_click` and do not double-count `web_cta_click`.
- [ ] Confirm `product` is omitted because the Project is already PromptPro-specific.
- [ ] Confirm website events use `web_` and future extension events use `extension_`.
- [ ] Confirm `environment` is omitted only when staging and production are separated or Mixpanel is not used in staging.

### Conversion

- [ ] Store clicks by page and location.

### Content

Do not create a complex funnel or a user profile report in the first version.
