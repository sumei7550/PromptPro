# PromptPro 官网技术方案

更新时间：2026-08-21

本文档用于确定 PromptPro 官网 MVP 的工程边界、技术选型、目录组织、国际化、SEO 基础能力和部署方向。本阶段只完成方案设计，不创建官网项目，不安装依赖，不修改插件源码或构建配置。

## 1. 官网工程边界

### 1.1 独立目录

推荐官网使用独立的 `website/` 目录，与当前 Chrome 插件源码并列：

```text
promptpro/
├── src/                 # Chrome 插件源码
├── public/              # Chrome 插件静态资源和隐私页面
├── dist-new/            # Chrome 插件构建产物
├── store-assets/        # 商店和官网可复用的真实素材
├── docs/seo/            # 官网规划、事实和验证文档
└── website/             # 后续创建的官网工程
```

官网不应直接放入 `src/`、`src/popup/` 或 `src/content/`，也不应把官网页面混入插件的 Vite/CRXJS 入口。

### 1.2 是否独立仓库

当前阶段推荐先使用当前仓库中的独立目录，不立即拆分独立仓库。原因是：

- 官网早期需要频繁参考 `PRODUCT_FACTS.md`、验证记录、真实截图和 Chrome Web Store 信息；
- 个人开发者维护一个仓库的成本更低，便于同步产品事实和文案；
- 官网尚未确定域名、部署方式、语言路由和内容规模，过早拆仓库会增加流程成本。

当官网拥有独立发布节奏、内容团队、独立权限或需要公开开源官网源码时，再考虑迁移到独立 repository。无论是否拆仓库，官网都必须保持与插件独立构建、独立部署。

### 1.3 与 Chrome 插件源码的关系

官网是产品介绍、隐私说明、平台状态、模板展示和 Chrome Web Store 转化入口，不是插件运行时的一部分。

官网可以复用或引用：

- 已确认的产品事实；
- 已验证的支持平台和限制；
- 真实插件截图；
- 真实模板标题、描述和公开示例；
- Chrome Web Store 安装链接。

官网不得直接依赖插件运行时的 `chrome.*` API，不读取用户的本地模板、历史或设置，也不将用户私有数据同步到官网。

官网文案以 `PRODUCT_FACTS.md` 和当前验证记录为事实依据。代码中存在的适配器或平台配置不等于官网可以宣传的当前支持能力。

### 1.4 与 dist/build 产物隔离

- 官网使用自己的源码目录、依赖清单和构建输出目录，例如 `website/dist/` 或部署平台的构建目录；
- Chrome 插件继续输出到现有 `dist-new/`，官网不写入、覆盖或修改该目录；
- 官网构建不应成为插件 `npm run build` 的隐式步骤，插件构建也不应依赖官网；
- `dist/`、`dist-new/`、`node_modules/` 等生成物不作为官网源码提交；
- 发布时分别验证插件压缩包和官网静态产物，避免把官网文件打入扩展或把扩展文件部署到网站。

## 2. 技术方案比较

PromptPro 官网首版需要首页、功能页、隐私页、平台页和模板页，后续可能增加平台详情、模板分类和教程内容。三种方案均可实现静态部署，但适用侧重点不同。

| 维度 | 方案 A：Next.js 静态生成 | 方案 B：Astro 静态站点 | 方案 C：Vite + React 静态部署 |
|---|---|---|---|
| SEO 能力 | 支持静态预渲染、metadata、路由级生成和结构化数据，能力完整 | 默认输出静态 HTML，内容型 SEO 和页面级 metadata 很强 | 可以生成静态页面，但需要自行设计路由、metadata、sitemap 和预渲染方案 |
| 页面速度 | 静态生成可很快，但容易引入较多 React/框架运行时代码 | 默认较少客户端 JavaScript，适合内容页和高 Lighthouse 目标 | 页面可很快，但 React 组件通常需要客户端加载，需主动控制脚本体积 |
| 国际化支持 | 路由、静态参数和生态成熟，适合 `/en/`、`/zh-CN/` | 可用多语言路由和内容集合实现，轻量但需要项目自行约定 | 可实现，但路由、语言资源、预渲染和 hreflang 多数需要自行维护 |
| 部署复杂度 | 静态导出可部署到多种平台；若误用服务端能力会增加复杂度 | 输出纯静态文件，部署简单，适合 Cloudflare Pages、Netlify 等 | 静态部署简单，但 SEO 预渲染和内容组织需额外工程约束 |
| 后续扩展能力 | 生态最大，适合未来动态功能、CMS、服务端能力，但复杂度和成本也更高 | 适合持续增加平台页、模板页、教程和内容集合，也可嵌入 React 组件 | 适合小型产品站和交互组件；内容规模增大后需自行补齐约定和工具 |
| 个人开发者维护成本 | 中等偏高 | 低到中等 | 低到中等，取决于自建 SEO 和内容方案的完整程度 |
| 与当前需求匹配度 | 能力充足，但存在过度设计风险 | 高 | 中等，首版可行但需要承担更多基础设施工作 |

### 2.1 方案 A：Next.js 静态生成

Next.js 适合需要复杂路由、内容系统、服务端能力或未来产品官网与应用逐步融合的项目。通过静态生成可以满足 SEO 和静态部署要求，但必须明确使用静态输出边界，避免引入不必要的服务端运行时、API Route、账号系统或动态数据依赖。

主要优点是生态和国际化实践丰富，后续扩展能力强。主要缺点是对当前 5 个静态页面而言偏重，配置和运行概念更多，容易让官网工程超出个人开发者的 MVP 范围。

### 2.2 方案 B：Astro 静态站点

Astro 面向内容型网站和静态页面，默认尽量输出 HTML，仅在需要交互的组件上加载客户端 JavaScript。它适合 PromptPro 的首页、功能说明、隐私页面、平台总览、模板内容和后续教程。

Astro 可以嵌入 React 组件，因此不妨碍复用少量现有前端经验；同时可以通过内容集合或明确的页面数据结构管理平台和模板内容。国际化、sitemap、metadata 和结构化数据可以按项目约定实现，不需要为了首版引入服务端后端。

主要代价是团队和生态规模不如 Next.js，部分国际化和内容工作流需要自行选择和维护。对当前个人开发者项目而言，这一代价可接受。

### 2.3 方案 C：Vite + React 静态部署

Vite + React 与当前插件技术栈接近，创建和部署小型静态站点很直接，适合页面数量少、交互较多、SEO 要求有限的项目。它可以作为成本最低的快速方案。

但官网的核心价值包含搜索入口和可索引模板内容，单纯客户端渲染会增加 SEO 风险。若采用该方案，需要额外处理静态预渲染、路由、页面级 metadata、canonical、sitemap、hreflang 和结构化数据，最终可能重新构建一套内容站能力。

## 3. 推荐方案

推荐：**Next.js App Router + TypeScript + Vercel，使用独立 `website/` 目录，当前保持静态优先。**

推荐原因：

1. PromptPro 首阶段是 SEO 内容型官网，不是需要账号、数据库或服务端逻辑的 SaaS；
2. Next.js App Router 支持静态生成、页面级 metadata、sitemap、robots、Open Graph 和结构化数据；
3. 当前页面使用静态生成和尽量少的客户端组件，保持首屏速度和 SEO 优先；
4. 后续增加平台详情页、模板分类页、教程页、账号、云同步、在线模板库或用户中心时，可以在同一应用架构中扩展；
5. Vercel 与 Next.js 的构建、预览、部署和回滚流程集成度高，减少单独维护部署适配的成本；
6. 与 Chrome 插件构建链路解耦，降低误改插件配置和混淆发布产物的风险；
7. 当前阶段不使用数据库、不接入登录、不接入后端 API、不接入分析或遥测，未来能力只保留架构扩展空间，不提前实现。

Astro 和 Vite + React 仍是可行备选，但本次不再作为推荐方案。Astro 更适合纯内容站，Vite + React 则需要自行补齐更多 SEO 预渲染和内容组织约定；当前选择 Next.js 的重点是保留未来应用能力，同时通过静态优先约束控制 MVP 复杂度。

## 4. 项目结构建议

### 4.1 当前推荐结构

```text
promptpro/
├── src/
│   ├── background/      # Chrome 插件
│   ├── content/         # Chrome 插件
│   ├── popup/           # Chrome 插件
│   └── shared/          # Chrome 插件共享逻辑
├── public/              # 插件静态资源、locale 和隐私页面
├── store-assets/        # 真实产品和商店素材
├── docs/
│   └── seo/             # 官网规划、事实、验证和技术方案
├── dist-new/            # 插件构建产物，不属于官网
└── website/             # 后续官网 Next.js 工程
    ├── public/          # favicon、OG 图片、robots 等公开静态资源
    ├── src/
    │   ├── components/  # 官网展示组件
    │   ├── content/     # 模板、平台和教程等公开内容
    │   ├── layouts/     # 页面布局和 SEO 基础组件
    │   └── pages/       # /、/features、/privacy、/platforms、/templates
    └── .next/            # 官网构建缓存/产物，不与 dist-new/ 混用
```

### 4.2 为什么这样组织

- 插件和官网拥有不同运行环境、发布目标和隐私边界；
- `website/` 让官网可以独立安装依赖、构建和部署，不污染插件脚本；
- `docs/seo/` 保留产品事实和验证依据，便于文案更新前审查；
- 公开模板和平台内容放在官网内容目录，但必须来自已确认事实，不读取用户数据；
- 独立的 `website/dist/` 与 `dist-new/` 物理分开，发布检查更容易。

### 4.3 未来拆分独立仓库的条件

满足以下任一条件后，可考虑将 `website/` 拆为独立 repository：官网需要独立协作者和权限、官网部署与插件发布完全不同、内容更新频率明显高于插件、或官网需要独立 issue/CI/域名管理。拆分前应保留事实文档同步机制，避免官网文案脱离插件实际能力。

## 5. 国际化方案

### 5.1 路径规划

推荐使用独立语言路径，避免同一 URL 根据浏览器状态返回不同语言：

```text
/en/
/en/features/
/en/privacy/
/en/platforms/
/en/templates/

/zh-CN/
/zh-CN/features/
/zh-CN/privacy/
/zh-CN/platforms/
/zh-CN/templates/
```

默认语言推荐为 `zh-CN`，因为当前产品和开发维护以中文为主；英文页面作为独立内容维护，而不是简单把中文页面机器翻译后混用。若部署或品牌策略最终要求英文默认，可在域名和首页策略确定后调整，但必须保持 URL、canonical 和重定向规则一致。

### 5.2 hreflang 与 metadata

- 每个中文页面指向对应英文页面的 `hreflang="en"`；
- 每个英文页面指向对应中文页面的 `hreflang="zh-CN"`；
- 两者都可增加 `hreflang="x-default"` 指向语言选择页或默认语言页；
- 每个语言版本使用自己的 canonical，不把中文和英文页面 canonical 到同一 URL；
- `title`、`description`、H1、OG 文案和结构化数据中的文本随语言切换；
- 翻译页面必须保留同一产品事实边界，不因语言不同夸大平台支持或隐私承诺。

## 6. SEO 基础能力清单

首版官网应包含以下能力：

- `sitemap.xml`：只收录真实存在、可访问和希望被索引的页面；
- `robots.txt`：允许公开产品页，避免收录构建内部路径、预览路径和不应公开的内容；
- 页面级 `title` 和 `meta description`；
- 每页唯一 H1，以及清晰的 H2/H3 层级；
- `canonical`：防止语言路由和尾斜杠造成重复页面；
- Open Graph：标题、描述、站点名和真实产品预览图；
- Twitter Card：兼容社交分享预览；
- favicon 和必要的图标资源；
- 中英文 `hreflang`；
- `SoftwareApplication`：描述 PromptPro Chrome 扩展，但只填写已确认事实；
- `Organization`：官网品牌和官方链接；
- `WebSite`：站点名称和规范 URL；
- `BreadcrumbList`：仅在页面确实存在层级导航时添加；
- `FAQPage`：仅对页面真实展示且符合规则的 FAQ 使用；
- `Article`：未来教程页面需要时再添加；
- 图片 `alt` 文本、尺寸和压缩；
- 全站导航和上下文内链；
- 结构化数据中的 URL、名称和描述与页面可见内容一致。

RSS 不是首版必需能力。只有在后续持续发布教程、更新日志或其他时间序列内容时，才建议增加 RSS；静态产品页和模板总览不需要为了 SEO 强行加入 RSS。

## 7. 部署方案

官网部署目标已确定为 Vercel。四个平台仍作能力和成本对比参考，但本项目的正式技术组合调整为 Next.js + Vercel。最终上线仍需结合域名、DNS、国内访问测试和实际构建结果确认。

| 平台 | 国内访问 | 全球 SEO 与稳定性 | 成本 | 后续维护 | 适合度 |
|---|---|---|---|---|---|
| Vercel | 中国大陆访问速度和稳定性需实测，部分网络环境可能不一致 | 与 Next.js 集成深，全球部署和预览体验好 | 有免费层，超出额度后按用量计费 | Git 集成、预览、回滚和后续动态能力扩展简单 | 首选，需先做国内访问验证 |
| Cloudflare Pages | 全球边缘网络较好，国内实际体验取决于区域、DNS 和网络环境 | 静态站点、CDN、HTTPS 和自定义域名能力强 | 静态托管成本低，免费层适合 MVP | 配置相对简单，生态与 Astro 匹配 | 高，适合静态官网 |
| Netlify | 国内访问需实测 | 静态部署、预览和表单等能力成熟 | 有免费层，按使用量扩展 | 上手简单，功能较完整 | 中高，但国内链路需验证 |
| GitHub Pages | 国内访问可能受网络和资源加载影响 | 静态页面稳定，但动态能力和边缘控制较少 | 公共仓库场景成本低 | 维护简单，适合纯静态文档 | 中，适合作为低成本备选 |

### 7.1 推荐部署方向

正式推荐使用 **Vercel**：

- 与 Next.js App Router、静态生成和后续动态路由能力集成；
- Git 推送后的预览、生产部署、日志和回滚流程适合个人开发者；
- 当前可以只部署静态生成页面，不需要数据库、登录或后端 API；
- 后续若增加账号、云同步、在线模板库或用户中心，可以在同一部署体系中扩展，而不必更换官网平台。

Vercel 不是对国内访问的自动保证。上线前必须用目标域名和真实页面测试国内访问、英文页面、静态资源、Chrome Web Store 链接和搜索引擎抓取情况。

### 7.2 部署决策因素

- 国内访问：检查首页、语言页面、图片、字体和 Chrome Web Store CTA 是否可访问；
- 全球 SEO：确认 HTTPS、规范 URL、页面响应、sitemap 和 Search Console 验证；
- 成本：首版不引入数据库、服务器和按请求计费的后端；
- 维护：优先 Git 推送即构建、失败可见、可回滚的平台；
- 隐私：默认不接入广告、分析或遥测；如需安装点击统计，先完成数据流和隐私审查；
- 域名：在域名确定前不写死最终 canonical、OG URL 和 sitemap 地址。

## 8. 本阶段不执行

本阶段明确禁止以下操作：

- 不创建 `website/` 官网项目；
- 不初始化 Next.js、Astro 或 Vite 工程；
- 不安装任何官网依赖；
- 不修改根目录或官网的 `package.json`、`package-lock.json`；
- 不修改 Chrome 插件 `src/`、`public/`、`manifest`、Vite/CRXJS 或其他构建配置；
- 不修改、覆盖或清理 `dist-new/`、其他 `dist*` 产物和 `node_modules/`；
- 不部署网站、不绑定域名、不配置 DNS；
- 不接入分析、广告、遥测、账号、后端 API 或远程提示词处理；
- 不生成未经事实文档和验证记录支持的平台承诺、模板数量或隐私结论；
- 不因本技术方案恢复或修改既有删除状态的 `doc/` 文件。

## 9. 下一阶段开发任务

在方案获得确认后，建议按以下顺序执行：

1. 确定官网是否继续使用当前仓库的 `website/` 目录，以及正式域名和默认语言；
2. 按 Next.js App Router + TypeScript + Vercel 方案定义独立的官网 `package.json`、脚本和构建输出；
3. 核对 `PRODUCT_FACTS.md` 与当前版本验证记录，冻结首版可公开事实；
4. 整理真实截图、模板公开示例、Chrome Web Store URL 和 favicon 素材；
5. 创建官网工程和基础布局，只实现 `/`、`/features`、`/privacy`、`/platforms`、`/templates`；
6. 加入中英文路径、页面级 metadata、canonical、hreflang、OG、robots、sitemap 和基础 JSON-LD；
7. 使用静态构建验证页面 HTML、链接、资源、语言切换和构建产物隔离；
8. 在部署平台上做国内访问和全球页面抓取测试；
9. 部署后提交 sitemap，并根据真实搜索曝光和安装点击数据决定是否扩展平台详情页、模板分类页和教程页。

本阶段输出是技术方案，不代表官网工程已经创建，也不代表任何平台支持、域名、部署平台或当前版本能力已经重新验证。
