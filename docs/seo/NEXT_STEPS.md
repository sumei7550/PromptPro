# PromptPro 官网与插件重构：下一步执行方案

更新时间：2026-08-21

## 1. 当前判断

PromptPro 已经有一个上架版本，因此不需要等待插件全面重构完成后再做官网。

当前版本应作为可用基线：

```text
现有上架版本
    -> 官网 MVP 与安装转化
    -> 当前版本真实验证
    -> 收集用户反馈
    -> 根据真实问题确定重构范围
    -> 官网内容与稳定功能同步扩展
```

不建议采用以下两种顺序：

```text
全面重构 -> 再做官网
```

或：

```text
完整 SEO 官网 -> 再确认插件真实能力
```

更适合个人开发者的方式是：先做官网定位和 MVP，同时以真实用户反馈驱动插件重构。

## 2. 立即执行的第一步

先完成当前上架版本的产品事实盘点，形成官网和插件重构共同使用的事实来源。

建议后续新增：

```text
docs/seo/PRODUCT_FACTS.md
```

需要确认的内容：

| 项目 | 需要确认 |
|---|---|
| 支持平台 | 哪些平台经过真实 Chrome 验证并可以正常使用 |
| 一键优化 | 中文、英文是否都正常 |
| 模板数量 | 当前实际可用数量 |
| 模板分类 | 写作、编程、营销等分类是否准确 |
| 模板搜索 | 中英文关键词是否都能搜索 |
| 自定义模板 | 当前版本是否稳定 |
| 优化历史 | 是否稳定、是否需要重构 |
| 本地存储 | 数据实际保存在哪里 |
| 远程请求 | 是否存在 API、统计或远程资源 |
| 权限 | Manifest 中的权限是否都必要 |
| 首次使用 | 新用户能否快速理解操作方式 |
| 已知问题 | Chrome 商店评价和个人测试中的问题 |

当前项目已经具备可用于官网宣传的产品素材，包括：

- 本地提示词优化；
- 66 个中英双语模板；
- 多个 AI 平台适配；
- 模板搜索；
- 中英双语界面；
- 本地存储；
- 自定义模板和历史相关能力。

但是，代码中已经配置的能力不等于官网可以直接承诺的能力。平台支持和核心流程必须经过真实 Chrome 验证后再公开宣传。

## 3. 官网 MVP 范围

第一版官网只做以下页面：

```text
/
/features
/privacy
/platforms
/templates
```

### 首页

首页负责转化，必须包含：

- 产品一句话定位；
- 当前真实功能；
- 已验证的支持平台；
- 真实产品截图；
- 本地隐私卖点；
- Chrome Web Store 安装按钮；
- FAQ；
- 中英文切换。

### 功能页

介绍当前已经稳定的功能：

- 一键优化；
- 模板库；
- 模板搜索；
- 自定义模板；
- 中英双语；
- 本地存储；
- 其他已经验证的能力。

### 隐私页

明确说明：

- 是否需要账号；
- 提示词是否上传；
- 数据保存位置；
- 是否存在远程处理；
- 是否有分析、广告或遥测；
- 使用了哪些浏览器权限；
- 是否会自动提交消息。

官网隐私文案必须与代码、Chrome Web Store 描述和实际发布版本保持一致。

### 平台页

第一版可以先做平台总览，后续再拆分为：

```text
/platforms/chatgpt
/platforms/claude
/platforms/gemini
/platforms/deepseek
```

每个平台页需要包含真实支持说明、截图、使用步骤、限制、FAQ 和安装 CTA。

### 模板页

第一版可以先做模板总览，后续再拆分为：

```text
/templates/writing
/templates/coding
/templates/marketing
/templates/academic
```

模板页需要提供真实可用的模板内容，不应只有 SEO 文案和安装按钮。

## 4. 当前版本实测范围

官网制作期间，应同步对已上架插件做一次真实 Chrome 验证。

至少覆盖：

```text
ChatGPT + 中文输入
ChatGPT + 英文输入
空输入
较长输入
优化结果写回
模板搜索
模板插入
自定义模板
历史记录
刷新页面后再次使用
```

记录以下问题：

- 用户是否知道如何启动优化；
- 浮动按钮是否容易找到；
- 输入框识别是否稳定；
- 优化失败是否有明确提示；
- 结果是否会意外覆盖原提示词；
- 是否可以撤销或恢复；
- 模板插入是否稳定；
- 页面刷新后插件是否仍然正常；
- 是否出现控制台错误；
- 不同平台的体验是否一致。

建议后续新增验证记录：

```text
docs/seo/CURRENT_VERSION_VALIDATION.md
```

## 5. 重构优先级

### P0：影响首次成功使用

- 用户不知道如何启动优化；
- 浮动按钮找不到；
- 输入框识别失败；
- 优化结果没有正确写回；
- 空输入没有提示；
- 模板插入失败；
- 原始提示词被意外覆盖。

### P1：影响留存和评价

- 模板搜索不准确；
- 模板分类混乱；
- 历史记录不好用；
- 多平台体验不一致；
- Popup 和页面内功能行为不一致；
- 首次使用引导不清楚。

### P2：影响长期维护

- 平台适配器重复；
- 共享类型混乱；
- 状态管理不统一；
- 存储迁移困难；
- 测试难以补充；
- 新平台接入成本过高。

不要仅因为代码可以重写就进行全面重构。优先解决影响用户首次成功使用、留存和评价的问题。

## 6. 官网与插件的并行工作流

### 官网轨道

目标：让现有版本获得更多安装和用户反馈。

工作内容：

- 首页；
- 功能页；
- 隐私页；
- 平台总览；
- 模板总览；
- Chrome Web Store CTA；
- 基础 SEO；
- Search Console；
- 简单的访问和安装点击统计。

### 插件轨道

目标：提高安装后的首次成功率、留存和评价。

工作内容：

- 收集当前版本问题；
- 按用户影响排序；
- 先修复 P0 问题；
- 再重构核心数据模型或平台适配层；
- 逐个平台验证；
- 按小版本发布；
- 维护更新日志。

两条轨道的关系：

```text
官网负责获客
插件负责激活和留存
重构负责提高体验
官网内容负责解释和转化
```

## 7. 三个工作日执行计划

### 第 1 天：产品事实盘点

输出：

```text
docs/seo/PRODUCT_FACTS.md
```

内容：

- 当前功能；
- 已验证平台；
- 未验证平台；
- 当前限制；
- 隐私和权限；
- 已知问题；
- 官网可用文案；
- 暂时不能宣传的内容。

### 第 2 天：官网 MVP 设计

输出：

```text
docs/seo/WEBSITE_MVP.md
```

内容：

- 首页结构；
- 页面路由；
- 每页 Title；
- 每页 Description；
- H1；
- CTA；
- 页面内链；
- 首版需要的截图；
- 中英文文案范围。

### 第 3 天：当前插件真实验证

输出：

```text
docs/seo/CURRENT_VERSION_VALIDATION.md
```

内容：

- 测试环境；
- 验证平台；
- 核心流程结果；
- 失败项；
- 严重程度；
- 是否需要重构；
- 是否可以在官网宣传。

完成这三个文档后，可以明确回答：

- 当前版本哪些能力可以宣传；
- 哪些问题必须先修；
- 哪些模块值得重构；
- 官网第一版应该写什么。

## 8. 最终执行顺序

```text
产品事实清单
    -> 官网 MVP
    -> 当前版本 Chrome 实测
    -> 重构任务拆解
    -> 官网上线
    -> 根据真实数据扩展 SEO
```

核心原则：

> 当前上架版本是可用基线，官网负责放大它，重构负责修复真实问题。
